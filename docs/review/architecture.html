一个小家，一台服务器。

全栈 Node.js，共用 TypeScript 类型。以单实例、低成本、可恢复为目标；用清楚的边界应对同步和金额正确性，不为两个人搭建复杂基础设施。

推荐组合： Next.js App Router + TypeScript + Tailwind CSS + Zod + Drizzle ORM + SQLite。
正式工程已落地于 src/；本页为离线架构说明，不连接真实账本。全部账单通过 /records 独立页面查询。

需要知道的限制

ECS 是单点，发生故障时服务不可用。保留机外副本，才有完整的数据恢复路径。

为什么推荐这套，而不是继续加服务

组成 推荐 理由 / 边界
全栈框架 Next.js App Router + TypeScript React 页面与 Node API 放在一个工程、一个部署单元；Route Handler 负责 HTTP，业务逻辑独立。
页面样式 Tailwind CSS v4 + CSS 变量 统一米白、墨灰、暗红令牌；不叠加大型后台组件库。正式工程的交互组件使用可访问性基础组件。
数据校验 Zod 复用字段定义；客户端改善反馈，服务端重新校验金额、身份与账本权限。
数据访问 Drizzle + better-sqlite3 类型化 schema 与可版本化迁移；适合低写并发单实例。原生驱动需匹配 Linux 架构和 Node 版本。
登录会话 账号密码 + 数据库存储的服务端会话 密码使用成熟库的 Argon2id；随机会话 token 仅在 Cookie，数据库只存摘要。生产前完成专门安全验证。
状态与请求 React 本地状态 + fetch 少量页面无需全局状态库；统一 runtime 处理加载、错误、刷新与草稿。
部署与运行 Caddy + systemd + Node.js LTS 自动 HTTPS、进程重启；建议在本地或 CI 构建 Linux 产物，避免低配 ECS 执行重型构建。
数据图表 CSS 条形图，后续按需 SVG 第一期展示分类和付款占比即可，不为几根柱子增加大型图表依赖。

费用边界

  • ECS 是主要持续费用，带宽、磁盘按实际套餐计算。
  • 域名若已有可复用；新购域名会产生额外年费。
  • HTTPS 证书可免费；公网证书通常需域名和正确 DNS。
  • 大陆服务器的公开网站通常需要备案；按实际部署地区处理。

运行与恢复

  • 单 Node 实例，数据库存放在发布目录之外。
  • SQLite WAL + busy timeout + 短事务；不启用多实例。
  • 每天使用 SQLite backup API / 在线备份命令生成一致快照。
  • 机外保存加密副本，并定期在临时库中验证恢复。

从「保存账单」到「两个人都看见」

浏览器 · 校验并生成 requestId

金额转整数分，带上本次请求标识；设置保存中状态并保留表单。

POST /api/ledgers/:id/entries

同域 HTTPS；会话取当前用户；检查 Origin / CSRF 防护、Zod 字段约束及请求大小。

业务服务 · 鉴权和规则校验

确认当前成员、付款人成员资格、分类与日期合法。created_by 由服务端身份设置，不接受客户端冒充。

SQLite · 一个短事务

检查幂等标识：已成功则返回原记录；否则写入 Entry 与 MutationRequest 并提交。

响应成功 · 再更新页面

返回服务端记录和版本。刷新账单及概览后提示已保存；失败时保留输入，不把未保存数据混进统计。

另一台手机 · 重新验证数据

初次打开、页面重新可见、手动刷新时拉取最新账单。API 使用 private, no-store，避免共享数据被缓存。

失败不是「丢掉输入」

  • 400 / 字段错误
    在对应输入旁提示，保留整张表单。
  • 401 / 会话失效
    提示重新登录；当前页保留草稿，第一期不承诺刷新后恢复。
  • 403 / 非成员
    拒绝操作；不展示其他账本数据。
  • 409 / 版本冲突
    展示最新值，保留本地改动供用户比较。
  • 超时 / 网络中断
    显示未确认状态；同 requestId 重试，防止重复账单。
不引入 WebSocket。第一期采用打开 / 回到页面 / 手动刷新时同步；两台手机同时保持前台时不会自动实时更新。

API 边界

接口 行为 约束
POST /api/auth/session 账号密码登录 失败限速、通用错误信息、数据库会话；仅初始化与邀请允许创建账号。
GET /api/ledgers/:id/data 首页月度概览、分类、成员与当前用户模板 成员鉴权，首页取最近 8 笔；月度统计不随明细筛选改变。
GET /api/ledgers/:id/reports 日/月/年支出折线与同范围收支、分类、成员汇总 granularity=day + period=YYYY-MM；month + YYYY；year 为历年。成员鉴权、只读快照、按账单日期聚合；空白日期补零，软删除排除，不受列表分页限制。
GET /api/ledgers/:id/entries
GET /api/ledgers/:id/entries/export 		独立账单页的高级分页查询与全量 CSV start/end、kind、categoryIds、memberId、creatorId、minAmount/maxAmount（分）、search、sort、page；同账本鉴权、过滤一致，列表每页 30 笔，汇总/导出包含全部匹配项。
POST /api/ledgers/:id/entries 新增收支 金额整数分、幂等标识、服务端推导创建人。
PATCH / DELETE /api/ledgers/:id/entries/:entryId 修改或填写原因后软删除账单 WHERE ledger_id + entryId + version；成功后版本递增。删除必传 reason，other 需填写 reasonNote（最多 200 字），原因随删除事务保存。
POST /api/ledgers/:id/categories 动态新增共享分类 可编辑成员；同账本、同收支类型内名称唯一。
GET / POST /api/ledgers/:id/templates
PATCH / DELETE /api/ledgers/:id/templates/:templateId 		查询、新增、修改、删除我的模板 user_id 来自会话，所有查询和修改限定 ledger_id + user_id；无法读取或修改对方模板。
POST /api/ledgers/:id/invites 生成一次性邀请 仅创建者、有效期、可撤销；第二名成员加入后不能再使用。
POST /api/invites/accept 创建伴侣账号并加入 有效 token；消费邀请、成员上限与账号创建采用事务。
GET /api/ledgers/:id/export 导出 CSV 成员鉴权、过滤一致、转义引号和公式前缀、分页读取大数据量。

User 是独立模块，认证与账本各有边界

user / 用户

User：稳定身份、显示名称、账号状态

负责当前用户资料查询、昵称修改和身份生命周期；停用时保留历史引用。首期不增加用户管理后台或公开用户搜索。

GET /api/users/me
PATCH /api/users/me

身份来自会话；PATCH 仅接受 display_name，不接受 user_id、权限、disabled_at 或密码字段。

auth / 认证

Session：登录、退出、密码验证、会话

负责密码哈希与验证、登录限速、会话创建和撤销。通过注入的服务端凭据接口取得认证所需字段，不将 password_hash 返回浏览器。

POST /api/auth/session
DELETE /api/auth/session

登录确认账号有效；每次受保护请求重新检查会话和用户状态，不能只在登录时检查停用状态。

ledger / 账本

Ledger、Membership、Invite
Category、Entry、MutationRequest

负责账本数据、成员角色和邀请名额。一个用户在不同账本可拥有不同角色，owner / editor 不作为 User 的全局角色字段。

/api/ledgers/:id/…

每次访问都按目标账本检查成员身份；「已登录」不等于「有权访问这个账本」。
模块不等于独立服务。user、auth、ledger 仍在同一个 Node.js 应用和数据库内；首期不为拆模块增加部署或基础设施成本。

跨模块流程由 server/flows 组合

  • 创建账号 / 接受邀请：流程协调器组合 user 的身份创建、auth 的密码处理、ledger 的邀请与成员规则，并在同一个事务内完成持久化。
  • 停用账号：先处理仍由该账号管理的账本，user 更新状态，auth 撤销会话；事务统一提交，账单与历史身份不删除。
  • 依赖方向：HTTP 适配 → flow → 模块服务 → 仓储。模块服务不互相 import；协调层注入跨模块能力和事务上下文。
  • 字段归属：User 行由 user 仓储维护；账号与密码的专用访问能力仅供认证流程使用，个人资料读取与更新采用字段白名单。后续新增第三方登录时再迁移独立认证身份表。

前端单向依赖

L5 · UI 渲染和输入；调用 runtime，可以消费纯规则，不直接调用 HTTP 或写库。
L4 · Runtime 收集登录上下文，管理提交 / 加载 / 错误，调用 service；不堆积计算规则。
L3 · Service 金额 / 分类规则与客户端流程；不依赖 React、DOM 或 Provider，通过参数接收 ctx。
L2 · Repo 浏览器请求与响应转换；不决定 UI 生命周期，不导入 runtime。
L1 · Config 静态展示配置与默认值，只依赖类型；可配置分类由数据库经 Repo 获取。
L0 · Types 数据形状、业务语言，不依赖上层。
UI → Runtime → Service → Repo → Config → Types。允许依赖更低层；禁止反向依赖。只有逻辑层要求，不强制建立六层目录。

浏览器和服务器之间有一条硬边界

浏览器 feature 交互状态 + HTTP Repo
HTTP / JSON schema 校验 · 会话身份
server-only 服务端 Service → SQL Repo → SQLite

客户端不能 import 数据库、密码逻辑和服务端会话；server-only 模块由构建边界限制。服务端业务服务通过参数接收身份，并在每次操作重新鉴权。

避免重复业务逻辑

共享 schema 定义数据约束；客户端规则负责及时反馈，服务端规则具有最终权威。SQL 仓储只存取数据，不引用 React。跨域操作由显式协调流程组合，不让两个业务 Service 互相依赖。

验证重点

  • 金额精度、月份归属与统计一致性。
  • 未登录 / 非成员无法读取或修改账单。
  • 重复提交只记一笔，旧版本不能覆盖新修改。
  • iPhone 与鸿蒙实机的键盘、日期选择、弹层。
  • 备份可恢复，升级前迁移可在副本上验证。
